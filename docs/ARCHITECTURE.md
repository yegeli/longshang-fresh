# 架构说明

## 当前系统：V0.4

当前是原生 HTML、CSS 与 JavaScript ES Modules 组成的静态站点。源码直接位于 `dist/`，无需构建；Node.js 静态服务器用于本地预览，不提供业务 API。模型与浏览器存储测试使用 Node.js 自带的测试工具。

| 文件或目录 | 职责 |
| --- | --- |
| `dist/index.html`、`app.js`、`experience.js`、`styles.css` | 买家路由、页面、购物车与收藏等交互 |
| `dist/admin.html`、`admin.js`、`admin.css` | 商品、素材、订单与售后管理演示 |
| `dist/model.js` | 商品与规格校验、整数分金额、购物车报价、订单快照、发货与售后状态 |
| `dist/catalog-store.js` | 商品目录的读取、校验、保存与上下架 |
| `dist/media-store.js` | 本机素材校验、IndexedDB 存储及浏览器播放地址 |
| `dist/specialty-content.js`、`ui.js` | 指南与专题内容、图标与 HTML 转义 |
| `dist/assets/` | 内置示意素材及对应来源记录 |
| `tests/` | 模型与目录持久化的自动化测试 |

本地入口为 `/` 与 `/admin.html`，另兼容 `/admin`。买家路由使用 URL hash。当前后台无需登录，因为它只能修改该站点来源下的本浏览器演示数据。

## 数据如何流转

1. 页面通过 `catalog-store.js` 读取商品目录，并更新模型中的当前目录。
2. 组件从同一目录显示规格、价格、上架状态与素材编号。
3. 报价以整数分计算；生成订单时保存名称、规格、单价、数量及合计快照。
4. 后台操作通过模型校验，再写入同一来源的订单存储。其他标签页通过 `storage` 事件重新读取。
5. 媒体文件由 IndexedDB 保存，商品仅记录素材编号；页面读取文件后生成临时对象 URL。临时 URL 不作为持久化素材地址。

| 位置 | 内容与限制 |
| --- | --- |
| `localStorage` | 商品、订单、购物车、收藏与足迹，以及示例订单初始化标记；不跨设备共享 |
| `sessionStorage` | 当前选中商品、规格、数量与示例地区；用于当前标签页恢复 |
| IndexedDB | 本地选择的图片与视频文件；不是云上传 |
| 页面内存 | 客服演示对话、编辑表单与临时素材播放地址 |

沿用既有 `longshang-demo-*` 存储键以兼容旧演示记录。不同站点来源互不共享数据，复制源码也不会迁移浏览器中的记录。清空站点数据会同时影响商品、订单和本机素材。

## 现有业务约束

- 每款商品保留 `small`、`family` 两种规格，价格为整数分。
- `draft`、`published`、`offline` 控制是否可新增加购与结算；已知链接仍可展示下架商品，旧订单不因此丢失。
- 同一商品与规格在购物车合并；一笔订单可包含多行商品，模拟运费按合并订单收取一次。
- 订单主状态为 `created`／`cancelled`；模拟发货记录放在 `fulfillment`，售后使用独立的 `submitted`／`resolved`／`withdrawn` 状态。
- 订单保存成交时的名称、规格与金额；目录改价不重新计算历史订单。售后当前针对整笔订单，未实现逐项退款。
- 商品和后台订单写入失败须报错；部分买家本地数据可退回内存并提示用户，不能视为可靠服务器存储。

浏览器数据可被本机用户修改。当前金额校验和状态保护用于演示一致性，不是身份认证、访问隔离或交易安全方案。

## 下一阶段：替换存储，增加服务端校验

以下是拟议设计，当前仓库尚未提供这些业务接口。先采用一个应用服务与持久化数据库，媒体使用受控文件或对象存储；具体框架和部署方式在接口约定确定后选择，避免先拆分多个服务。

| 拟议接口组 | 负责内容 | 必须由服务端校验 |
| --- | --- | --- |
| `/api/v1/session` | 登录状态、退出与角色读取 | 身份、会话有效性、管理权限 |
| `/api/v1/products` | 买家已发布目录与后台编辑、发布、下架 | 商品授权范围、字段与价格、版本冲突 |
| `/api/v1/media` | 上传、归属、读取与商品绑定 | 文件内容与大小、访问权限、素材归属 |
| `/api/v1/orders` | 报价、创建、查询、备注与模拟发货 | 当前商品状态、服务端金额、订单归属、状态与重复请求 |
| `/api/v1/orders/:id/after-sales` | 整单售后申请、撤回与处理意见 | 申请人权限、重复申请、状态流转与处理者权限 |

接口名称是讨论起点，不作为已实现的契约。请求与响应字段、错误码、权限和幂等规则需先补齐示例并测试。

实施中应保留以下边界：

- 服务端重新读取商品与运费计算报价，使用事务保存订单快照；重复创建请求使用稳定的请求标识避免生成多单。
- 顾客只能访问自己的订单；运营只能处理授权商品和订单；素材记录上传者与归属，直接调用接口也要校验。
- 商品、素材绑定和状态修改记录操作者与版本；编辑冲突应提示，不能静默覆盖其他人的修改。
- 前端通过存储／接口适配层读取数据，逐步替换 `localStorage`，保持现有页面和核心业务用例可回归。
- 本地演示记录默认留在演示环境；迁移测试资料时明确选择、校验与备份，不混入正式数据。
- 支付与真实物流另行设计，不把模拟发货记录当作真实履约凭证。

对应交付与进入试运营的条件见 [路线图](ROADMAP.md)。
